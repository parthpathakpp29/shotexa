# Spike A — Smart Screenshot Stitching: results

Status: **complete, awaiting review.** Scope: exactly two vertically-scrolling screenshots,
PNG/JPEG/WebP, similar widths. No ORB/feature fallback. No production UI.

Raw data: [`results/stitch-benchmark-browser.json`](results/stitch-benchmark-browser.json),
[`results/stitch-benchmark-node.json`](results/stitch-benchmark-node.json).

## How to reproduce

```bash
npm run fixtures:stitch   # regenerate fixtures (Playwright/Chromium renders)
npm test                  # unit tests (Vitest)
npm run bench:stitch      # Node benchmark → results/stitch-benchmark-node.json
npm run test:e2e          # browser benchmark + manual-correction/export flow (Playwright)
npm run dev               # prototype at http://localhost:3000/spikes/stitch
```

`/spikes/stitch` returns 404 in production builds unless `SHOTEXA_ENABLE_SPIKES=1`, and is `noindex`.

## Architecture used

```text
React (src/app/spikes/stitch/stitch-spike.tsx)        ← no OpenCV, no worker details
   │  stitchEngine.analyse(blobA, blobB) / .compose(plan)
   ▼
src/core/stitch/engine.ts   (facade; lazily creates workers)
   │  typed protocol v1: RUN/CANCEL → PROGRESS/SUCCESS/ERROR/CANCELLED (src/workers/protocol.ts)
   ├─► vision.worker.ts  → OpenCV.js (self-hosted, loaded on first job) → analyseStitch()
   └─► image.worker.ts   → composeStitch(): OffscreenCanvas, ORIGINAL full-res blobs
src/core/stitch/*  pure, testable algorithm:
   analyse.ts · static-bands.ts · residual.ts · confidence.ts · plan.ts · gray.ts
   matcher.ts (TemplateMatcher interface) · opencv-matcher.ts (only OpenCV adapter)
   sources.ts (StitchImageSource: ImageBitmap in browser / RGBA in Node tests)
   config.ts (every provisional threshold)
```

- OpenCV is reachable only through `TemplateMatcher`. Swapping engines means writing one adapter.
- `StitchImageSource` lets the *same* algorithm run in the browser worker and in Node benchmarks.
  Full-resolution pixels are only materialised for a ≤192-row refinement strip per image.
- The main thread only decodes 360-px-wide preview bitmaps. Analysis decodes happen in the worker.
- Screenshots never leave the page. The Playwright test asserts that no non-GET or
  body-carrying request happens during 17 analyses and an export.

## Algorithm

1. **Validate:** widths within 2%. Controlled error codes, e.g. `STITCH_WIDTH_MISMATCH`.
2. **Proxies:** greyscale, width ≤ 360 px, same scale for both images.
3. **Static bands (§30):** find rows identical at the same y in A and B (status bar, app bar,
   sticky nav, input bar, cookie bar). Two variants are produced:
   - *strict:* every row matches.
   - *tolerant:* rows with localised changes (clock/battery) are allowed within the top/bottom 6% edge zone.
4. **Band hypotheses:** tolerant → strict → none. Each is evaluated fully; the most confident wins.
   There's an early exit once one reaches `high`. This fixes periodic content, where a zebra table
   scrolled by a multiple of its row height looks like fixed chrome.
5. **Template matching (OpenCV `TM_CCOEFF_NORMED`):**
   - templates of 6/12/24% of the content height;
   - cut from **the bottom of A** and matched against B's content;
   - cross-checked with templates from **the top of B** matched against A.
   Flat templates slide toward texture. Each match records its best score, its second-best peak
   outside ±4 rows (ambiguity) and any x drift.
6. **Vote:** cluster candidate offsets (±1.5 proxy rows), score-weighted.
7. **Proxy residual:** mean absolute difference (MAD) over the content overlap at the chosen
   offset ±2, compared with a baseline median over all other offsets.
8. **Full-resolution refinement:** map to full-res (`dy / scale`). Search ±(1/scale + 2) px using
   MAD on the most textured ≤192-row band. Then measure the **ink mismatch**: the fraction of
   text/edge pixels that disagree. A true scroll overlap is pixel-identical, so this is ~0.
9. **Confidence:**
   - weighted similarity 0.20, uniqueness 0.20, agreement 0.20, residual contrast 0.25, seam/ink 0.15;
   - hard caps for low similarity, low residual contrast and ink mismatch > 10%;
   - high ≥ 0.80, medium ≥ 0.55, otherwise low;
   - any capped result (< 0.30) becomes `no-match`, placed end to end so nothing is lost.
   All values live in `src/core/stitch/config.ts`.
10. **Plan/compose:** the seam goes in the middle of the window between B's header and A's footer.
    The output keeps A's header and B's footer and is drawn from the original files at full resolution.
11. **Manual correction:** numeric input, slider, ±1/±10 buttons (44 px), ↑/↓ and Shift+↑/↓ on the
    preview, "Reset to automatic", normal/difference preview, swap A/B.
    Confidence is shown as text, e.g. "Confidence: 61% — please review this join."

## Fixtures

17 pairs are generated by `scripts/spikes/stitch-fixtures/generate.ts`. Each is a real Chromium
render of synthetic pages (chat, article, code editor, invoice table) captured at two known scroll
positions, so `expected offset = Δscroll × DPR` exactly. Phone fixtures change the status-bar
clock and battery between shots. All content is synthetic.

Summary:

- **Offsets:** 15/15 overlapping fixtures that are within scope are pixel-exact.
  13 of them are automatic and 1 (table-rows) needs review. The out-of-scope tiny-overlap stress
  case is flagged, not solved.
- **Non-overlapping:** 2/2 rejected.
- **Wrong results at high confidence: 0.** This is enforced as a test assertion.
- **Node vs browser:** the Node path gives the same classes and offsets. Only resampling differs
  (area average vs Chromium's `drawImage`).

## Failure cases and what they taught

| Case | Behaviour | Root cause | Status |
|---|---|---|---|
| Tiny overlap (24 px of 800) | no-match → end-to-end + manual | At 0.28× the overlap is ~7 proxy rows, smaller than the smallest template. Higher-res proxies don't fix it (sweep: 480/640 px still miss it and cost 1.7–3× the time). | **Open.** Needs a dedicated edge-zone pass (below) |
| Periodic table, v1 | Offset was wrong by 400 px, yet rated *medium* | Rows aligned by the scroll period looked "static", so band detection ate 30% of each edge. Blurred proxy text and white-dominated MAD hid the error. | **Fixed:** band hypotheses + full-res ink-mismatch cap |
| Phone status-bar drift, v1 | Correct offset but confidence capped to low | The clock and battery changed, so the band stopped at 65 px instead of 321 px and B's app bar polluted the overlap. | **Fixed:** drift-tolerant edge zone |
| Capped confidence = no-match threshold | Browser returned "matched/low" at exactly 0.30 | `lowCap == noMatchBelow` | **Fixed:** cap 0.25; unit test pins `lowCap < noMatchBelow` |

Still untested (not in fixtures): horizontally drifting or zoomed pairs; unequal widths beyond 2%;
dynamic content inside the overlap (video, carousels, caret, "typing…" indicators, relative
timestamps); OS-specific screenshot compression; Retina desktop captures; screenshots with a
transient toast or overlay in one frame only; reversed order (B above A); 3+ screenshots.

## Memory and performance

Measured on Windows desktop, Chromium via Playwright, warm worker:

| | Phone 1170×2532 | Desktop 1280×800 | WebP 2560×1600 |
|---|---|---|---|
| Decode (both, in worker) | 30–40 ms | 11–24 ms | 65 ms |
| Analysis total | 165–370 ms | 55–200 ms | 104 ms |

- **OpenCV cold load:** 1.1–1.4 s in the browser (fetch from localhost, plus WASM compile and init).
  Real networks add download time for 2.7 MB (brotli). The load happens once per session per worker.
- **Heaviest case:** non-overlap-chat (~370 ms) runs all three band hypotheses, because nothing
  reaches `high` early.
- **Per-analysis working set:**
  - two decoded bitmaps: 2 × 11.8 MB for phone screenshots (in the worker, closed afterwards);
  - two ~280 KB proxies;
  - two ≤192-row full-res strips (~0.9 MB);
  - small transient OpenCV Mats (all `delete()`d in `finally`).
  - The main thread holds only 360-px preview bitmaps (~0.5 MB each).
- **OpenCV runtime:** loading it costs ~68 MB of process memory in Node (parse + WASM compile +
  heap). Expect a similar order in the browser worker. This counts against the 192 MiB soft
  budget (§40) and is the dominant cost, not the images.
- **Compose:** one full-res OffscreenCanvas (1170×5064 RGBA ≈ 23.7 MB) plus PNG encode.
  Very tall outputs will hit canvas limits. That is Spike B's job (tiling/segmented export).
- **Cancellation:** cooperative, checked between stages. Bitmaps are closed and Mats deleted on every path.

## Bundle / WASM implications

- `@techstark/opencv-js@5.0.0-release.1` is a **full OpenCV build with the WASM inlined as base64**:
  13.3 MB raw / 3.76 MB gzip / 2.67 MB brotli. Stitching uses three functions from it:
  `matFromArray`, `matchTemplate`, `delete`.
- Bundling it through Turbopack failed: its Node-only `require("fs")` branch, then CJS-interop
  breakage around its Promise export. It is now **self-hosted as a versioned static asset**,
  `/vendor/opencv/opencv-<version>.js`, copied by `scripts/copy-vendor-assets.mjs` (`predev`/`prebuild`).
  The module worker loads it with a bundler-ignored `import()`. This matches §53
  ("stable processing asset URLs, self-hosted WASM").
- **Verified in a production build:**
  - the homepage references no OpenCV or worker code, so it loads 0 bytes of OpenCV (§48);
  - app chunks contain no OpenCV;
  - the vision worker chunk is 14 KB raw / 5.9 KB gzip;
  - the image worker chunk is similar;
  - OpenCV is fetched only on the first analysis.
- **CSP:** WASM compilation needs `script-src 'wasm-unsafe-eval'`, plus `'self'` for the vendor
  script and `worker-src 'self'`. No COOP/COEP or SharedArrayBuffer is needed; the build used is
  single-threaded.

## What must change before production Smart Stitching

1. **Replace the 13 MB OpenCV build.** Either:
   - a custom OpenCV.js build with only `core` + `imgproc`, with the WASM as a separate
     streaming-compiled `.wasm` file (likely ~1–2 MB). Needs a build pipeline; or
   - a pure-TS/SIMD-WASM normalised cross-correlation. On ≤360-px proxies the whole search is
     small, so this could be a few KB. `TemplateMatcher` already isolates this choice.

   **Recommendation:** benchmark a pure-TS NCC matcher against these fixtures before committing to
   any OpenCV build. The architecture lists OpenCV.js, so this is flagged as a proposed
   configurable-implementation change, not a stack change. OpenCV may still earn its place for the
   later ORB fallback and Compare.
2. **Tiny-overlap pass:** when no hypothesis reaches `high`, run a second matcher on only A's last
   ~15% and B's first ~15% of content at higher resolution, with templates sized to that zone.
3. **Seam placement:** the midpoint of the valid window is naive. Choose the lowest-difference,
   lowest-edge row, so the seam avoids text and dynamic content that differs between shots.
4. **Hypothesis cost:** three passes on hard cases. Cache proxy crops and residual baselines
   across hypotheses, or rank hypotheses more cleverly.
5. **Confidence calibration:** the weights and thresholds are tuned on 17 synthetic pairs.
   Collect a **real-device** benchmark set (iOS/Android native screenshots, WhatsApp/Telegram,
   Safari/Chrome desktop captures, Retina) and calibrate so "high" has a measured error rate.
   The architecture's fixture list still lacks unequal widths, low contrast and very long
   screenshots.
6. **N > 2 screenshots and ordering:** analyse adjacent pairs and detect a reversed pair
   (a negative offset means "swap?").
7. **Width mismatch:** scale-normalise within tolerance instead of cropping to the common width.
8. **Large outputs:** compose in tiles and segments. Depends on Spike B's canvas/bitmap limits
   (Safari, iOS).
9. **Integrate with the real runtime:** WorkerBroker (one heavy job at a time), AssetRegistry
   (Blobs outside Zustand), operation history for seam edits (undo/redo), analytics mapping
   (`stitch_confidence` buckets, controlled error codes only).
10. **Cross-browser:** only Chromium was run. Firefox/WebKit Playwright projects and real iOS
    Safari testing are required, since `createImageBitmap` resize options and OffscreenCanvas
    support differ.
