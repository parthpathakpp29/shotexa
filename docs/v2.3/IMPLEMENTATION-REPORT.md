# Shotexa V2.3 Phase A — Smart Privacy Redaction

**Release-candidate evidence note (22 October 2026):** The named browser screenshots, exports, and measurement files below are preserved in the local release archive outside Git. They are listed as evidence descriptions rather than links because they are not in this candidate.

## Scope and readiness

Phase A extends the existing Safe Share/Privacy Guard at `/redact-screenshot`. All image analysis and redaction remain in the browser. No account, cloud storage, upload endpoint, mandatory watermark, or HEIC production path was added. Phase B and C below are proposals only.

## What changed

- **Face suggestions:** an optional YuNet scan detects possible faces locally. Suggestions enter the existing finding review list. Accepting one creates a normal editable redaction region, so move, resize, keyboard nudging, undo/redo, and Blackout/Blur/Pixelate all use the existing canvas.
- **Oriented photos:** workspace dimensions now come from the browser's decoded preview rather than only the file header. This keeps regions aligned when an EXIF rotation swaps the displayed width and height.
- **Plate workflow:** optional OCR pattern matching suggests readable Indian-style registration strings. It does **not** detect a vehicle or identify a physical license plate. Manual rectangles remain the reliable fallback for international, unreadable, angled, or missed plates.
- **Detector choice:** text categories, face scan, QR/barcode, and plate-text suggestions can be selected independently. A visual-only face scan skips OCR. Unavailable detectors and images over 25 megapixels (12 megapixels on devices reporting 4 GB RAM or less) lead to a clear manual fallback.
- **Review gate:** Safe Share prepares a flattened, metadata-cleaned image in temporary browser memory, displays those exact bytes at full size, offers a before/after comparison, and requires an explicit review checkbox before the copy enters the workspace or download, clipboard copy, and Continue With links become available. Leaving without review discards the temporary copy.
- **Continuation:** the reviewed artifact ID, not the original ID, is passed into Beautifier (including Screenshot Packs), Editor, PDF, Compress, Privacy Clean, Batch, Extract Text, Annotate, and Combine. Screenshot Packs and Batch replace an original with its Safe Share copy in multi-image selection, including Select All. The source remains separately editable in the in-memory workspace.
- **SEO:** improved the existing redaction page and FAQ to explain face blur, screenshot privacy, and honest plate limitations. No duplicate landing page or search-volume claim was added; canonical and sitemap behavior remain based on the existing tool registry.

## Reused systems

The existing Privacy Guard OCR detectors, barcode support, finding review, RedactionCanvas, undo/redo store, full-resolution `renderSafeShare`, metadata-clean and decode verification, AssetRegistry, same-origin ONNX Runtime deployment script, worker broker, tool registry, and Continue With mechanism were reused. The original screenshot bytes are never edited. The exported copy is re-encoded from the composed canvas and contains no editable redaction layer or embedded source image.

## Security and privacy decisions

- Blackout writes opaque black pixels into a full-resolution canvas before encoding. It does not rely on an SVG, CSS, PDF, or annotation overlay. Blur and pixelation remain optional, with a warning that they can be less secure.
- The export is encoded as PNG/JPEG/WebP, cleaned through the existing metadata engine, decoded again, and checked for output dimensions and metadata-clean verification.
- No image or OCR content is sent to an AI API. The model, WASM runtime and OCR language files are same-origin, loaded only when needed. Browser tests monitor outgoing requests with image bodies.
- The face worker is terminated after each scan to release its heap. Bitmaps and temporary canvases are closed/reset. Images over 25 megapixels, or over 12 megapixels on devices reporting 4 GB RAM or less, use manual selection instead of forcing a face-model decode.
- A prepared copy is held only in the browser's temporary asset registry until review; only confirmation publishes it into the in-memory workspace. An abandoned copy is revoked. Uploaded screenshots are not saved permanently by this feature.
- A face or plate not detected automatically is **not** evidence of safety. Users must inspect the final image before download or continuation.

## Performance and known limits

The fixed-input YuNet model is small, but inference requires a 640×640 tensor and temporary decode. Accuracy falls for tiny, profile, obscured, or unusual faces. It does not identify people. The plate OCR rule covers familiar Indian-style registration text only; it can miss plates and can suggest similar non-plate text. Barcode support varies by browser. The current Playwright WebKit environment reports face inference unavailable; the UI shows this and retains manual redaction. A page-canvas ONNX fallback was tried and removed because it stalled editing in that environment. The final output preview may take time on large images; manual editing remains available even when a detector fails.

The real face fixture tests one visible face. Unit tests decode two face boxes, but this is not a demographic or cross-device accuracy benchmark. Users must inspect the entire output, especially near faces, text, and plates. Blur and pixelation are convenience effects; use opaque Blackout for sensitive information. No search-volume figures are claimed for the SEO edits.

## Phase B architecture proposal — Safe Share Links (approval required)

Keep cloud sharing a separate, explicit action **after** the Phase A review gate. Upload only the final approved, flattened artifact. Suggested boundaries: a short-lived object-storage bucket with server-generated opaque IDs, signed upload/download requests, optional password verification with a slow password hash, per-link expiry and deletion jobs, rate limits, upload size/type limits, abuse reporting, and audit records without storing source screenshots. The UI must clearly state that recipients and the storage provider can access the finalized image until expiry. Hosting, region, provider, retention, cost ceiling, key management, and abuse policy require owner approval before implementation. Candidates should be evaluated against the project's hosting environment and privacy obligations; no provider is selected here.

## Phase C architecture proposal — Screenshot Review & Approval (approval required)

Build review links on top of the approved Phase B access model. Store comments as normalized text with coordinates tied to immutable artifact dimensions/version; never attach comments to an unreviewed original. A review session needs link scope, reviewer identity policy, password or invitation access, comment moderation, status transitions (pending/approved/changes requested), revision history, notification consent, retention/deletion, and rate limiting. Decide whether anonymous reviewers are allowed, who can see comments, and how approval is revoked before selecting a database or service. No collaboration code or cloud storage is included in Phase A.

## Local testing

On `codex/shotexa-v2-3`, run `npm install` only if dependencies are absent, then `npm run dev -- --port 3100`. Visit `http://localhost:3100/redact-screenshot`, upload a PNG/JPEG/WebP image, choose scan categories, review suggestions, drag a manual region where needed, select Blackout for secrets, prepare the safe copy, inspect it, tick the review checkbox, then download or Continue With. Run `npx tsc --noEmit`, `npm run lint`, `npm run test`, `npm run build` (which invokes the HEIC exclusion guard), `npx playwright test src/tests/e2e/v23-privacy.spec.ts --project=chromium --project=webkit`, and `git diff --check`.
